# Junior/Middle
### 1. JVM nima?

`JVM` - Java bytecode'ni bajarish uchun JVM Specification(JVMS) tomonidan belgilangan abstract execution machine/runtime environment. JVM bytecode'ni platformadan mustaqil tarzda execute qilish uchun standartlashtirilgan runtime modelini taqdim etadi. 

JVM'ning bytecode execution modeli `stack-based` hisoblanadi: instruction'lar operandlar bilan asosan har bir method frame ichidagi `Operand Stack` orqali ishlaydi. Har bir method chaqirilganda JVM Stack'da yangi Frame hosil bo'ladi; Frame ichida `Local Variables`,`Operand Stack` va method execution uchun zarur runtile ma'lumotlari mavjud.

`JVM Specification` JVM qanday behavior va execution modeliga ega bo'lishi kerakligini belgilaydi, `HotSpot` esa shu specification'ni implement qilubchi konkret JVM implementation hisoblanadi.

JVM bytecode'ni to'g'ridan-to'g'ri CPU instruction sifatida bajarmaydi. JVM implementation bytecode'ni `Interpreter` orqali execute qilish yoki `JIT` compiler yordamida platformaga mos native machine code'ga compile qilib, CPU'da bajarishi mumkin.

Shu sababli Java bytecode bir xil qolgan holda turli platformalarda mos JVM implementation orqali bajarilishi mumkin.

### 2. `.java` va `.class` o‘rtasidagi farq nima?
`.java` fayl — bu dasturchi yozgan manba kod bo‘lib, inson o‘qiy oladigan sintaksisda yoziladi. JVM uni bevosita bajara olmaydi. Shuning uchun javac kompilyatori .java faylni .class faylga — ya’ni bytecodega aylantiradi.

`.class` fayl — bu JVM kontrakti. Unda qat’iy format mavjud:
 - `Magic number (0xCAFEBABE)` — faylning haqiqiy class fayl ekanini bildiradi.
 - `Constant pool` — stringlar, metod nomlari, fieldlar va literal qiymatlar saqlanadi.
 - `Access flags` — class public/final/abstract ekanini ko‘rsatadi.
 - `Fields`, `Methods`, `Attributes` — kod va metadata.

JVM .class faylni ClassLoader subsystem orqali yuklaydi, Verifier uni tekshiradi, so‘ng Execution Engine (Interpreter yoki JIT Compiler) orqali bajaradi.
Bajarilish jarayonida kod Runtime Data Areas (Heap, Stack, Metaspace) bilan bog‘lanadi va oxir-oqibat CPU mashina kodiga aylantiriladi.

------------------------------------------------------------------------------------------------------------------

### 3. Bytecode nima?
`Bytecode` — bu JVM uchun oraliq instruktsiyalar to‘plami, ya’ni `stack-based` virtual machine uchun yozilgan kod.

- Har bir bytecode instruktsiya `opcode + operand` formatida bo‘ladi.
  Masalan:
  - iload_0 → stack’ga birinchi lokal o‘zgaruvchini yuklaydi.
  - iadd → stack’dagi ikki qiymatni qo‘shadi.
  - invokevirtual → metod chaqiradi.

- Bytecode `constant pool` orqali `string literal`, `class nomlari`, `method imzolari` va `field nomlar`iga murojaat qiladi.
- `.class` faylda bytecode method body sifatida saqlanadi.
- JVM bytecode’ni dastlab `Interpreter` orqali bajaradi, keyin `Profiler + JIT Compiler` yordamida `mashina kod`iga o‘tkazadi.
- Shu mexanizm Java’ni platformadan mustaqil qiladi: .class fayl har qanday JVM’da ishlaydi, lekin oxir-oqibat CPU mashina kodiga aylantiriladi.

### 4. `javac` nima qiladi?
`javac` — bu Java kompilyatori. U `.java` fayldagi manba kodni `.class` faylga aylantiradi. Jarayon quyidagicha:
- **Lexical analysis** — kod tokenlarga bo‘linadi.
- **Parsing** — tokenlardan **AST (Abstract Syntax Tree)** hosil qilinadi.
- **Semantic analysis** — tiplar, metod chaqiruvlari, class ierarxiyasi tekshiriladi.
- **Bytecode generation** — **AST**’dan .class fayl tuziladi:
  - **Magic numbe**r (`0xCAFEBABE`)
  - **Constant pool** (stringlar, metod nomlari, fieldlar)
  - **Access flags** (public, final, abstract)
  - **Methods va attributes** (bytecode instruktsiyalar)
- **Output** — `.class` fayl JVM uchun universal bytecode formatida saqlanadi.
- Natijada, `.java` fayl → `.class` fayl → JVM → CPU mashina kodi oqimi hosil bo‘ladi.

### 5. JVM nima qiladi? 
  
`JVM` bytecode - CPU architecturega bog`liq bo'lmagan intermediate instruction set hisoblanadi. CPU esa Java yoki JVM bytecode haqida hech qanday ma'lumotga ega emas; CPU faqat o'zining architectureiga tegishli machine instructionlarni bajaradi. Shu sababli JVM Java bytecode bilan CPU o'rtasida abstraksiya qatlamini hosil qiladi. Bir xil .class bytecode Windows, Linux yoki ARM64 kabi turli  platformalarda ishlashi mumkin, chinki har bir platforma uchun mos JVM implementation mavjud. JVM implementation bytecodeni Interpereter orqali execute qilishi yoki JIT compiler orqali platformaga mos native machine codega compile qilish mumkin.

### 6. Interpreter nima?
**Interpreter** — bu JVM Execution Engine’ning bir qismi bo‘lib, bytecode’ni **instruction-by-instruction** bajaradi.

- `JVM` — `stack-based virtual machine`, shuning uchun Interpreter har bir opcode’ni stack ustidagi qiymatlar bilan ishlatadi.
- Masalan:
  - iload_0 → stack’ga lokal o‘zgaruvchini yuklaydi.
  - iadd → stack’dagi ikki qiymatni qo‘shadi.
   
- Interpreter odatda **switch-case loop** kabi ishlaydi: bytecode opcode’ni o‘qiydi, tegishli handler’ni chaqiradi, keyingi instruktsiyaga o‘tadi.

- Bu jarayon **oddiy va portativ**, lekin sekin — chunki har bir instruktsiya alohida interpretatsiya qilinadi.

- Shuning uchun **HotSpot**’da Interpreter faqat boshlang‘ich bajarish uchun ishlatiladi. Profiling orqali “hot” metodlar aniqlanadi va keyin `JIT Compiler` ularni mashina kodiga aylantiradi.

- Interpreter → Profiling → JIT → Code Cache oqimi Java’ni tez va samarali qiladi.

### 7. Stack-based JVM degani nima?

JVM stack-based virtual machine.
- Har bir metod chaqirilganda stack frame hosil bo‘ladi:
  - Local variable array.
  - Operand stack.
- Bytecode instruktsiyalari operand stack ustida ishlaydi (`iload`, `iadd`, `istore`).
- Afzalliklari: platform independent, oddiy implementatsiya.
- Kamchiliklari: register-based mashinalarga qaraganda sekinroq → JIT optimizatsiya zarur.

# Senior

### 8. JVM Stack va Operand Stack farqi nima?

`JVM Stack` — bu har bir thread uchun ajratilgan xotira maydoni. Har bir metod chaqirilganda stack frame hosil bo‘ladi. Stack frame ichida:
 - **Local variable array** — metod parametr va o‘zgaruvchilar.
 - **Operand stack** — bytecode instruktsiyalari ishlaydigan joy.
 - **Frame data** — return address va boshqa metadata.

`Operand Stack` — bu stack frame ichidagi operatsion maydon. Bytecode instruktsiyalari operand stack ustida ishlaydi:
 - `iload_1` → operand stack’ga qiymat push qiladi.
 - `iadd` → operand stack’dan ikki qiymatni pop qilib, natijani push qiladi.
 - `istore_2` → operand stack’dan qiymatni pop qilib, local variable array’ga yozadi.

**Xulosa:**
- JVM Stack — **thread-level container**.
- Operand Stack — **frame-level execution area**.
- JVM stack ichida operand stack mavjud, va u bytecode’ni bajarish uchun asosiy mexanizm hisoblanadi.

------------------------------------------------------------------------------------------------------------------

### 9. Stack Frame nima?

**Stack Frame** — bu JVM Stack ichida metod chaqirilganda hosil bo‘ladigan **execution konteyner**.

1. Metod chaqirilganda yangi stack frame yaratiladi.
2. **Local variable array** — metod parametrlarini va lokal o‘zgaruvchilarni saqlaydi.
3. **Operand stack** — bytecode instruktsiyalari shu yerda ishlaydi (iload, iadd, istore).
4. **Dynamic linking** — constant pool’dagi metod va fieldlarga murojaat qilish uchun pointerlar.
5. **Return address** — metod tugaganda qayerga qaytishni ko‘rsatadi.
6. **Exception handling data** — agar metodda xatolik yuz bersa, tegishli handler’ga yo‘naltiradi.

Metod tugaganda stack frame yo‘q qilinadi, va JVM Stack’dan chiqariladi.

------------------------------------------------------------------------------------------------------------------

### 10. Method chaqirilganda JVM'da nima sodir bo‘ladi?

1. Class Loading & Linking
  - Agar metod joylashgan klass hali yuklanmagan bo‘lsa, ClassLoader subsystem uni yuklaydi.
  - Linking bosqichida constant pool’dagi barcha external reference’lar (metod, field, class nomlari) tekshiriladi va bog‘lanadi.
  - Bytecode Verifier metodning bytecode’ini xavfsizlik qoidalariga mosligini tekshiradi (stack overflow, illegal access, type safety).

2. Stack Frame yaratish
  - Metod chaqirilganda JVM Stack’da yangi stack frame hosil bo‘ladi. Stack frame tarkibi:
  - Local Variable Array → metod parametr va lokal o‘zgaruvchilar.
  - Operand Stack → bytecode instruktsiyalari ishlaydigan joy (push/pop).
  - Dynamic Linking info → constant pool’dagi metod va field reference’lari.
  - Return address & metadata → metod tugaganda qayerga qaytishni ko‘rsatadi.

3. Bytecode Execution (Execution Engine)
  - Interpreter → bytecode’ni instruction-by-instruction bajaradi.
  - JIT Compiler → “hot” metodlarni profiling asosida mashina kodiga kompilyatsiya qiladi.
  - Code Cache → JIT kompilyatsiya qilingan kodni saqlaydi va qayta ishlatadi.
  - Operand stack ustida amallar bajariladi:
  - iload → qiymatni stack’ga push qiladi.
  - iadd → stack’dan ikki qiymatni pop qilib, natijani push qiladi.
  - istore → stack’dan qiymatni pop qilib, local variable array’ga yozadi.

4. Runtime Data Areas bilan ishlash
  - Heap → obyektlar va reference’lar saqlanadi.
  - Metaspace → klass metadata (field, method imzolari).
  - Thread Stack → har bir metod chaqiruviga stack frame qo‘shiladi.
  - PC Register → bajarilayotgan instruktsiya ko‘rsatkichini saqlaydi.

5. Method tugashi
  - Agar metod qiymat qaytarsa → operand stack’dan natija olinadi.
  - Stack frame JVM Stack’dan chiqariladi.
  - Control calling metodga qaytadi.
  - Agar exception yuz bersa → stack frame exception handler’ga yo‘naltiriladi.

### 11. Local Variable Table nima?

`**Local Variable Table**` — bu stack frame ichidagi komponent bo‘lib, metod parametrlarini va lokal o‘zgaruvchilarni saqlash uchun ishlatiladi. Har bir metod chaqirilganda JVM yangi stack frame yaratadi va uning ichida Local Variable Table hosil bo‘ladi.

📊 Tuzilishi va ishlash mexanizmi
 - Index-based storage: Har bir lokal o‘zgaruvchi indeks orqali aniqlanadi (0, 1, 2, ...).

 - Parametrlar joylashuvi:
   - Instance metodlarda index 0 → this reference.
   - Keyingi indekslar → metod parametrlar.
- Lokal o‘zgaruvchilar: Metod ichida e’lon qilingan o‘zgaruvchilar ham shu jadvalda saqlanadi.
- Tipga bog‘liq joylashuv:
   - int, float, reference → bitta slot.
   - long, double → ikkita slot egallaydi.

⚙️ Bytecode bilan ishlash
- iload n → Local Variable Table’dagi n-indeksdagi qiymatni operand stack’ga yuklaydi.
- istore n → Operand stack’dan qiymatni olib, n-indeksga yozadi.

Shu tarzda Local Variable Table ↔ Operand Stack o‘rtasida ma’lumot almashinuvi sodir bo‘ladi.

------------------------------------------------------------------------------------------------------------------

### 13. Operand Stack nima?

`Operand Stack` — bu stack frame ichidagi komponent bo‘lib, bytecode instruktsiyalari bajariladigan joydir. JVM **stack-based virtual machine** bo‘lgani uchun barcha amallar operand stack ustida push/pop orqali bajariladi.
  
🔧 Arxitektura darajasida rol
   - Operand Stack — metod bajarilishining markaziy qismi.
   - Har bir bytecode instruktsiya operand stack ustida ishlaydi.
   - Operand stack → data flow engine sifatida ishlaydi, local variable table bilan ma’lumot almashadi.
   - Bu dizayn CPU registerlariga bog‘lanmaganligi sababli platform independentlikni ta’minlaydi.

### 14. ClassLoader nima?

**ClassLoader** — bu JVM’ning **Class Loading subsystem** qismi bo‘lib, `.class` fayllarni xotiraga yuklash va namespace yaratish uchun javobgar. U Java dasturida klasslarni dinamik ravishda yuklaydi va JVM ichida ularni ishlatishga tayyorlaydi.  

---

##### 📊 ClassLoader vazifalari
1. **Loading**  
   - `.class` faylni diskdan, JAR’dan yoki tarmoqdan o‘qib, xotiraga yuklaydi.  
   - Har bir klass faqat bir marta yuklanadi va JVM ichida unikal identifikatorga ega bo‘ladi:  
     ```
     Class identity = ClassLoader instance + Class name
     ```

2. **Linking**  
   - **Verification** → bytecode xavfsizligini tekshiradi.  
   - **Preparation** → static fieldlar uchun default qiymatlar ajratadi.  
   - **Resolution** → constant pool’dagi external reference’larni (metod, field, klass) aniqlaydi.  

3. **Initialization**  
   - Static initializer (`<clinit>`) va static block’larni bajaradi.  
   - Klassni ishlatishga tayyorlaydi.  

---

##### ⚙️ ClassLoader Hierarchy
JVM’da **parent delegation model** ishlaydi:  
- **Bootstrap ClassLoader** → core Java kutubxonalar (`java.lang.*`, `java.util.*`).  
- **Extension ClassLoader** → `$JAVA_HOME/lib/ext` katalogidagi JAR’lar.  
- **Application ClassLoader** → `classpath`dagi foydalanuvchi klasslari va kutubxonalar.  

Delegation modeli:  
```
Application → Extension → Bootstrap
```
Ya’ni, har bir ClassLoader avval parent’iga murojaat qiladi, topa olmasa o‘zi yuklaydi.  

---

##### 🔧 Real hayotdagi misol
- **Tomcat server**: Har bir web-app uchun alohida ClassLoader yaratiladi. Shu sababli bir xil nomdagi `User.class` turli web-app’larda izolyatsiya qilinadi.  
- **Hot-reload**: Agar web-app qayta deploy qilinsa, eski ClassLoader unload bo‘ladi, yangi ClassLoader yangi versiyani yuklaydi.  

---

##### 🧠 Xulosa
- **ClassLoader** — JVM’da klasslarni dinamik yuklash mexanizmi.  
- U **loading → linking → initialization** jarayonlarini bajaradi.  
- Parent delegation modeli orqali xavfsizlik va izolyatsiya ta’minlanadi.  
- Har bir ClassLoader o‘z namespace’iga ega, shu sababli bir xil nomdagi klasslar turli ClassLoader orqali yuklansa, ular JVM ichida alohida obyekt sifatida qaraladi.

### 15. Parent Delegation Model qanday ishlaydi?

**Parent Delegation Model** — bu JVM’dagi **ClassLoader subsystem**ning asosiy dizayn tamoyili. U klasslarni yuklashda **hierarchical delegation**ni qo‘llaydi: har bir ClassLoader avval o‘zining parent’iga murojaat qiladi, faqat parent topa olmasa o‘zi yuklaydi.  

---

### 📊 Ishlash bosqichlari
1. **Application ClassLoader** biror klassni yuklashga harakat qiladi.  
2. U avval **parent ClassLoader**ga murojaat qiladi (Extension ClassLoader).  
3. Extension ClassLoader o‘z navbatida **Bootstrap ClassLoader**ga murojaat qiladi.  
4. Agar Bootstrap klassni topa olsa → uni yuklaydi.  
5. Agar Bootstrap topa olmasa → Extension o‘zi qidiradi.  
6. Agar Extension ham topa olmasa → oxirida Application ClassLoader o‘zi yuklaydi.  

---

### ⚙️ Hierarchy
- **Bootstrap ClassLoader** → Core Java kutubxonalar (`java.lang.*`, `java.util.*`).  
- **Extension ClassLoader** → `$JAVA_HOME/lib/ext` katalogidagi JAR’lar.  
- **Application ClassLoader** → `classpath`dagi foydalanuvchi klasslari.  

Delegation oqimi:  
```
Application → Extension → Bootstrap
```

---

### 🔧 Nega bunday yechim tanlangan?
1. **Xavfsizlik**  
   - Core API’lar (masalan, `java.lang.String`) faqat Bootstrap’dan yuklanadi.  
   - Foydalanuvchi o‘zining `String.class`ini qo‘shib JVM’ni aldolmaydi.  

2. **Barqarorlik va izolyatsiya**  
   - Har bir ClassLoader o‘z namespace’iga ega.  
   - Bir xil nomdagi klasslar turli ClassLoader orqali yuklansa, ular JVM ichida alohida obyekt sifatida qaraladi.  

3. **Deterministik yuklash tartibi**  
   - Klass qayerdan yuklanishini aniq bilish mumkin.  
   - Bu katta enterprise tizimlarda muhim.  

4. **Performance**  
   - Avval parent tekshiradi → ortiqcha qidiruv kamayadi.  

---

### 🧠 Xulosa
- **Parent Delegation Model** — ClassLoader’lar o‘rtasida **hierarchical delegation** tamoyili.  
- Har bir ClassLoader avval parent’iga ishonadi, faqat parent topa olmasa o‘zi yuklaydi.  
- Bu dizayn xavfsizlik, barqarorlik, izolyatsiya va deterministik yuklashni ta’minlaydi.

### 16. Loading, Linking va Initialization farqi nima?

JVM’da klass ishlatilishidan oldin u **Class Loading subsystem** orqali uch bosqichdan o‘tadi: **Loading → Linking → Initialization**.  

---

##### 1. **Loading**
- **Vazifa**: `.class` faylni xotiraga yuklash.  
- **Jarayon**:  
  - ClassLoader `.class` faylni diskdan, JAR’dan yoki tarmoqdan o‘qiydi.  
  - Klass uchun **namespace** yaratiladi.  
- **Natija**: Klass JVM ichida mavjud bo‘ladi, lekin hali ishlashga tayyor emas.  

---

##### 2. **Linking**
- **Vazifa**: Klassni ishlashga tayyorlash.  
- **Bosqichlari**:  
  1. **Verification** → bytecode xavfsizligini tekshiradi (stack overflow, illegal access, type safety).  
  2. **Preparation** → static fieldlar uchun default qiymatlar ajratadi (masalan, `int` uchun `0`).  
  3. **Resolution** → constant pool’dagi external reference’larni (metod, field, klass) aniqlaydi va bog‘laydi.  
- **Natija**: Klassning strukturasi to‘liq tekshirilgan va JVM ichida ishlashga tayyorlangan bo‘ladi.  

---

##### 3. **Initialization**
- **Vazifa**: Klassni ishga tushirish.  
- **Jarayon**:  
  - Static initializer (`<clinit>`) bajariladi.  
  - Static block’lar ishga tushadi.  
  - Static fieldlar explicit qiymatlari bilan to‘ldiriladi.  
- **Natija**: Klass to‘liq ishlashga tayyor bo‘ladi va undan obyekt yaratish yoki metod chaqirish mumkin.  

---

##### 📊 Farqlar jadvali

| Bosqich        | Vazifa                          | Natija |
|----------------|---------------------------------|--------|
| **Loading**    | `.class` faylni xotiraga yuklash | Klass JVM’da mavjud, lekin hali ishlashga tayyor emas |
| **Linking**    | Verification, Preparation, Resolution | Klass tekshirilgan va strukturasi tayyorlangan |
| **Initialization** | Static initializer va static block’larni bajarish | Klass to‘liq ishlashga tayyor |

---

##### 🧠 Xulosa
- **Loading** → Klassni xotiraga olib kirish.  
- **Linking** → Klassni tekshirish va tayyorlash.  
- **Initialization** → Klassni ishga tushirish (static block va fieldlar).

# Architecture

### 17. Nima uchun Java source code to‘g‘ridan-to‘g‘ri CPU tomonidan bajarilmaydi?

##### 1. **CPU faqat mashina instruktsiyalarni tushunadi**
- Har bir CPU (x86, ARM, RISC-V) faqat o‘zining **machine instruction set architecture (ISA)**ni bajaradi.  
- Java source code esa **high-level language** bo‘lib, sintaksis va semantik jihatdan CPU uchun bevosita bajariladigan formatda emas.  

---

##### 2. **Kompilyatsiya bosqichi zarur**
- Java source code → `javac` kompilyatori orqali **bytecode**ga aylantiriladi.  
- Bytecode — bu **platform-independent intermediate representation**.  
- CPU esa bytecode’ni tushunmaydi, uni faqat JVM orqali bajarishi mumkin.  

---

##### 3. **JVM arxitektura qatlamini hosil qiladi**
- JVM bytecode’ni **Interpreter** orqali instruction-by-instruction bajaradi yoki **JIT Compiler** orqali CPU mashina kodiga kompilyatsiya qiladi.  
- Bu jarayon CPU registerlariga bog‘lanmagan, balki **stack-based execution model** orqali ishlaydi.  
- Natijada, bir xil `.class` fayl turli platformalarda (Windows, Linux, ARM64) ishlay oladi.  

---

##### 4. **Platform independence**
- Agar Java source code to‘g‘ridan-to‘g‘ri CPU mashina kodiga kompilyatsiya qilinsa, har bir platforma uchun alohida kompilyator kerak bo‘lardi.  
- JVM esa **“Write once, run anywhere”** falsafasini ta’minlaydi: bir marta yozilgan kod turli platformalarda ishlaydi.  

---

##### 5. **Qo‘shimcha subsistemlar**
- JVM faqat source code’ni mashina kodiga aylantirib bermaydi, balki:  
  - **ClassLoader subsystem** → klasslarni dinamik yuklaydi.  
  - **Bytecode Verifier** → xavfsizlikni tekshiradi.  
  - **Garbage Collector** → xotirani boshqaradi.  
  - **JNI** → native kutubxonalar bilan integratsiya qiladi.  
- Bu subsistemlar CPU darajasida mavjud emas, faqat JVM orqali ta’minlanadi.  

---

##### 🧠 Xulosa
Java source code to‘g‘ridan-to‘g‘ri CPU tomonidan bajarilmaydi, chunki:  
- CPU faqat o‘zining mashina instruktsiyalarini tushunadi.  
- Java source code yuqori darajadagi abstraksiya bo‘lib, uni CPU bevosita bajara olmaydi.  
- JVM arxitektura qatlamini hosil qilib, bytecode’ni Interpreter yoki JIT orqali CPU mashina kodiga aylantiradi.  
- Shu dizayn Java’ni **platform-independent** qiladi va qo‘shimcha subsistemlar (GC, ClassLoader, Verifier)ni ta’minlaydi.
